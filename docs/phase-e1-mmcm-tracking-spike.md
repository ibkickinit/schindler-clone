# Phase E1 — MMCM phase-tracking spike

**Date:** 2026-05-18
**Audience:** The agent pivoting from TPG fsync debug to Phase E1.
**Status:** Spike brief. Scope, success criteria, and a seven-step iterative test plan that produces hard evidence at each step.
**Companion docs:** [`sync-architecture.md`](sync-architecture.md) (THE plan — read this first), [`tpg-sync-architecture-review.md`](tpg-sync-architecture-review.md) (why), [`tpg-vsync-alignment-debug.md`](tpg-vsync-alignment-debug.md) (parked record of why fsync-only doesn't work).

> **Framing reminder:** the PLL described here is **not** "a future phase" or "the upgraded version" of free-run. It is the always-on output-clock control loop the product is built around — see [`sync-architecture.md`](sync-architecture.md). The spike validates the loop with source vsync as the first available reference. Free-run is the same loop with integrator forced to zero; external genlock is the same loop with a different reference selected. One architecture, one code path, one set of bench tests.

## 1. Plain-English: what we were doing, and what we're doing now

### What we had been trying

Imagine two wristwatches on two different people's wrists. Each ticks at *almost* the same rate, but not exactly — one runs maybe 50 parts-per-million faster than the other. That's about 4 seconds of drift per day, or — for a video clock running at 60 frames per second — about one frame of drift every five minutes.

In the FPGA, those two "watches" are:

- **The source pixel clock** — recovered from the HDMI input (or, in TPG mode, just the same clock that the TPG is hung off of). This watch tells the source side "you are now on row 42 of frame 9001."
- **The output pixel clock** — generated by a separate clock generator (MMCM) inside the FPGA, driving the HDMI output. This watch tells the output side "you are now on row 42 of frame 9001."

The TPG writes its picture into a shared memory ring in *source time.* The output reads from the same ring in *output time.* Both sides agree on the layout of a frame (1920×1080 pixels, blanking intervals, etc.), but they don't agree on *when* row 0 starts.

The agent's attempts so far were all variations on **"line up the two watches at the start, then let them tick freely."** Attempt A used software to write a register at boot. Attempt B used a continuous hardware pulse. Attempt C used a one-shot hardware pulse. Attempt D gated that one-shot pulse on a confirmation that the output side was running. Each one improved the *initial* alignment, but none of them addressed the underlying physics: **two independent watches at the same nominal rate will always drift apart over time.**

The bench evidence (image #11) confirms it: even Attempt D's stable-looking picture is actually sliding, just slowly. The wrap point moves frame-by-frame because the clocks are slipping past each other in real time.

### What we're doing instead

Stop treating the two clocks as independent. Make one of them an active slave to the other.

The FPGA's MMCM (the chip that generates the output pixel clock) supports something called **dynamic reconfiguration**: while it's running, software can nudge its output frequency up or down by tiny fractional amounts — parts per million — by writing to its control registers (DRP). The MMCM keeps producing a clean, continuous clock the whole time; the only thing that changes is its exact rate.

So the new approach is a **software-closed phase-locked loop (PLL)**:

1. Every frame, measure the time difference between the output's vsync and the reference vsync (initially, the source's vsync; eventually, an external film-camera reference via the RP2040 + Si5351).
2. If the output vsync is *late*, nudge the MMCM to speed up by a tiny amount.
3. If the output vsync is *early*, nudge it to slow down.
4. Repeat forever.

This is the same idea as a thermostat. The thermostat doesn't try to predict the right heater setting in advance — it measures the room temperature, compares it to the target, and adjusts continuously. Within a few seconds the room settles to the target temperature and stays there indefinitely, even though the heater is being constantly nudged.

Once this loop is closed, the output clock is no longer "free-running." It's actively steered to track whatever reference we tell it to track. Drift stops because the two clocks aren't independent anymore.

The same architecture that locks output→source for the spike eventually locks output→external-genlock-reference for the product. The loop doesn't care what reference signal it's tracking, as long as something is providing one-edge-per-frame.

This is the "AHA" the debug-log user was asking for: the answer to "how do I align two oscillators?" is **you don't — you build a control loop that makes one chase the other.**

## 2. Scope of the spike

**In scope:**
- Software-closed loop on the PS, using existing `clk_wiz_pixclk_out` (or replace with a `clk_wiz` configured for DRP).
- Reference multiplexer with selectable inputs (source vsync, free-run/tied-low). Wired for additional reference inputs (Si5351 feedback, external sync recovery) even though those aren't populated at the bench yet — they just hang off unconnected mux inputs until the hardware exists.
- Lock state machine (Free-run / Acquiring / Locked / Holdover) with GPIO LED indicator.
- VDMA cadence cooperation: controller requests a frame slip when MMCM saturates.
- Goal: demonstrate that output vsync can be held within ±1 output line of any selected reference, indefinitely, and that MMCM-saturation handoff to VDMA frame-slip works as designed.

**Out of scope (deferred to later steps in [`sync-architecture.md §7`](sync-architecture.md)):**
- RP2040 / Si5351 hardware bringup. The spike validates the loop and the multiplexer; physical Si5351 integration plugs into the already-built mux input.
- Analog reference front-end (LTC / tri-level / black burst recovery). Separate hardware effort.
- Spec'd cadence conversion ratios (60→50, 3:2 pulldown, etc.). Spike validates that the VDMA-slip mechanism can be commanded by the controller; specific cadence schedules are configured later per output-rate selection.
- UI integration. The spike exposes status via UART and GPIO; the front-panel TFT and web UI wiring happens after the loop is proven.

**Pass criteria for the spike** — all must be true:
1. **Lock:** output vsync holds within ±1 output line of source vsync, indefinitely (30-minute soak).
2. **Free-run mode:** with reference deselected (mux tied low, integrator forced to zero), output runs at nominal rate, lock state correctly reports Free-run.
3. **Holdover:** with source vsync deliberately cut mid-run, output continues at last-tracked rate, lock state reports Holdover. On source return, re-locks within settling time.
4. **Cadence cooperation:** with a synthetic 1000 ppm rate offset injected, controller commands exactly one VDMA frame slip per accumulated frame of error, MMCM re-locks between slips.

If all four pass, the product's architectural foundation is in place.

## 4. Eight iterative tests, each producing hard evidence

Each test produces a number, a plot, or a binary pass/fail — not a "it looks better." Stop at the first failure and fix it before moving on. Tests 1–6 validate the MMCM phase loop in isolation. Tests 7–8 validate the dual-loop / reference-selector / holdover behavior that makes this the full architecture, not just a phase tracker.

### Test 1 — Measure the current drift rate

**Goal:** convert the current "moving wrap" bench evidence into a ppm offset between the two pixel clocks.

**Setup:** current build (Attempt D), TPG selected, capture stick connected.

**Procedure:**
1. Capture 30 seconds of video from the MS2109 (`ffmpeg -t 30 ...`).
2. For each frame, run the existing `analyze_tpg_capture.py` to extract the counter-overlay row.
3. Plot row vs frame number. Fit a straight line.
4. Slope (rows/frame) × frame rate (60 fps) = wrap velocity (rows/sec).
5. Convert to ppm: `ppm = (rows_per_sec / lines_per_frame) × (1 / frame_rate) × 1e6`. For 720p60: `ppm ≈ rows_per_sec × (1/720) × (1/60) × 1e6 ≈ rows_per_sec × 23.1`.

**Pass:** produces a single number — e.g., "the relative drift between source and output pixel clocks is 47 ppm."

**Why it matters:** sets the **required pull range** for the MMCM. If drift is 47 ppm, the loop must be able to slew the output clock by at least ±47 ppm (with margin — call it ±200 ppm) to capture and hold. The prior-art note documents ±500 ppm range, so we expect headroom, but confirm.

**Debug info to log:** raw row-per-frame data as CSV. Keep it — useful for plant identification in Test 3.

---

### Test 2 — Prove the MMCM actuator works open-loop

**Goal:** confirm that DRP writes to the MMCM actually change the output clock frequency. Don't close the loop yet.

**Setup:** any build with MMCM DRP exposed. Add a UART command like `m <hex>` that writes a single DRP register.

**Procedure:**
1. From firmware, baseline: read all DRP registers, log them.
2. Issue a single DRP write that should nudge the fractional divider by a small amount (say, +10 ppm equivalent).
3. Re-run Test 1's capture-and-fit procedure.
4. Compare wrap velocity before and after the nudge.

**Pass:** wrap velocity changes by the predicted amount (±20% tolerance), and the picture stays clean (no glitches, no DVI sink unlock).

**Why it matters:** if this fails, every later test is meaningless. Most common failure modes: DRP write sequence wrong (must observe handshake protocol), MMCM not configured for fractional reconfig, or reconfig requires a reset/lock-recovery sequence that drops the output. All three are recoverable but need to be solved here, not in the loop.

**Debug info to log:** DRP register dump before and after each write. Capture HDMI output during the write to detect glitches.

---

### Test 3 — Open-loop plant characterization

**Goal:** know exactly how many ppm of output-clock change you get per DRP step. This is the **plant gain** — required to design a stable closed-loop controller.

**Setup:** same as Test 2.

**Procedure:**
1. Sweep DRP-controlled offset across, say, 11 points: −50, −40, −30, ... +50 ppm (theoretical).
2. At each point, hold for 10 seconds, run Test 1's measurement to get actual measured wrap velocity (in ppm).
3. Plot measured ppm vs commanded ppm. Should be a line through the origin.

**Pass:** linear, monotonic, slope ≈ 1.0 within 10%.

**Why it matters:** if the plant isn't linear and monotonic, a simple PI controller won't be stable. Almost always passes for MMCM DRP — but verify, don't assume.

**Debug info to log:** full sweep CSV, plot it. Slope deviation from 1.0 indicates the DRP-to-ppm conversion formula needs calibration.

---

### Test 4 — First closed-loop attempt with source-vsync reference

**Goal:** close the loop and demonstrate that wrap motion stops.

**Setup:** PS firmware reads two timestamps — one captured on source vsync edge (via interrupt or polled GPIO), one captured on VTC TX vsync edge. Difference = phase error in pixel-clock periods. Convert to "lines of error."

**Controller (start with the simplest thing that could work):**
- Proportional-only, gain `Kp = 1.0` ppm-correction per line-of-error.
- Saturate the integrator to ±500 ppm.
- Apply the correction via Test 2's DRP-write mechanism, once per frame.

**Procedure:**
1. Boot. Note initial wrap velocity (should match Test 1).
2. Enable the loop.
3. Capture 60 seconds of output. Plot wrap row vs time.

**Pass:** wrap motion stops (within measurement noise) within 10 seconds of enabling the loop. Residual error bounded.

**Why it matters:** this is the spike's headline pass/fail. If wrap stops, the architectural argument is proven on the bench. If it doesn't, look at Test 5's diagnostic outputs before tuning gains.

**Debug info to log every frame, accessible via UART or `/proc`:**
- Source vsync timestamp
- Output vsync timestamp
- Computed phase error (lines)
- Commanded ppm correction
- Current MMCM DRP value
- Loop state (acquiring / locked / saturated)

A "locked" bit definition: |phase_error| ≤ 1 line for 60 consecutive frames. Surface it on a GPIO LED so you can see lock state without a UART connected.

---

### Test 5 — Disturbance response

**Goal:** measure the loop's settling time, overshoot, and steady-state error after a known disturbance.

**Setup:** Test 4's closed loop, locked.

**Procedure:**
1. Wait for lock.
2. Inject a step disturbance: write a fixed +100 ppm bias directly to the MMCM, bypassing the controller, for 1 frame.
3. Re-enable normal loop control.
4. Log phase error vs time for the next 30 seconds.

**Pass:** loop recovers to |phase_error| ≤ 1 line within 5 seconds, with overshoot < 5 lines.

**Why it matters:** characterizes the loop's transient response. Informs the eventual BW choice for the production loop (which the spec wants at ~0.5 Hz — *much* slower than the spike's interim BW).

**Debug info to log:** full phase-error-vs-time trace for each disturbance event. Save as CSV. Plot it.

---

### Test 6 — 30-minute soak

**Goal:** confirm no long-term failure modes (integrator wind-up, temperature drift, missed-frame edge cases).

**Setup:** Test 4's closed loop, locked.

**Procedure:**
1. Lock the loop. Confirm.
2. Run for 30 minutes. Log phase error every frame (108,000 samples).
3. Plot phase error distribution (histogram) and time series.

**Pass:**
- Phase error histogram is bounded — no entries beyond ±2 lines.
- No "unlock" events (the locked GPIO LED stays on for the entire run).
- No measurable trend in residual error vs time (i.e., the loop isn't slowly wandering off).

**Why it matters:** this is the actual production-relevant test. A loop that locks for 60 seconds is a demo; a loop that holds for 30 minutes is a foundation.

**Debug info to log:** full 30-minute CSV. Useful for future regression tests when the loop is later modified (e.g., when the reference is swapped from source vsync to Si5351).

---

### Test 7 — Dual-loop cooperation: MMCM saturation → VDMA frame slip

**Goal:** prove the architectural handoff between the phase loop (MMCM) and the rate loop (VDMA frame slip). When the rate offset exceeds what MMCM can absorb, the controller must release one frame slip, after which MMCM re-locks within its settling time.

**Setup:** Test 4's closed loop, locked. Add a synthetic rate-offset injector in firmware: a knob that biases the *reference timestamp* by a configurable fractional amount per frame, simulating a reference clock running at a different rate from the output.

**Procedure:**
1. Lock the loop with zero injected offset. Confirm steady state.
2. Inject a +1000 ppm rate bias on the reference timestamp. (1000 ppm > MMCM's ±500 ppm range, so MMCM must saturate.)
3. Observe controller behavior:
   - MMCM correction climbs to +500 ppm rail and saturates.
   - After ~N frames of saturation (N tunable, target 30–60), controller commands one VDMA frame skip.
   - MMCM phase error jumps by exactly one frame.
   - MMCM re-locks within its settling time (per Test 5).
4. Continue for 60 seconds. Count total frame slips. Expected slips/sec = injected ppm × frame rate / 1e6 = 1000 × 60 / 1e6 = 0.06 slips/sec, i.e., ~3.6 slips in 60 sec.
5. Disable injection. Confirm loop returns to zero-slip steady state within settling time.

**Pass:**
- Slips occur (controller is not stuck — MMCM doesn't ride the rail forever).
- Slip count matches predicted rate ±20%.
- Between slips, MMCM holds lock within ±1 line (rejecting injection-induced jitter is the loop's job).
- After injection ends, system returns to zero-slip steady state.

**Why it matters:** without this handoff, the architecture degrades to "MMCM loop with a hard 500 ppm range" — which fails for any cross-rate conversion (60→50 needs orders of magnitude more range than that). This test validates that the two loops cooperate as designed in [`sync-architecture.md §4`](sync-architecture.md).

**Debug info to log every frame:**
- Reference timestamp (with injection bias)
- Output timestamp
- MMCM correction value (with saturation flag)
- VDMA frame-slip events (timestamp + direction)
- MMCM saturation duration before each slip

CSV. Plot slip events over time; expected: roughly periodic, period determined by injected ppm.

---

### Test 8 — Reference selector and holdover

**Goal:** validate the user-facing reference-selector model. Free-run, Input-lock, and Holdover behavior must each be observable and correct.

**Setup:** Test 4's closed loop. Add a UART command `r <free|input>` to select reference mux state. Add a UART command `s` to simulate source disappearance (mask the source vsync edge detector).

**Procedure:**

**8a — Free-run:**
1. Boot with reference selector = Free-run (integrator forced to 0, mux tied low).
2. Confirm lock state reports `FREE-RUN`.
3. Measure wrap velocity (Test 1 procedure). Should match Test 1's baseline drift — i.e., loop is genuinely free-running.
4. Switch to Input-lock via UART. Confirm transition: `FREE-RUN → ACQUIRING → LOCKED`.

**8b — Holdover:**
1. Start locked (Input-lock mode, loop converged).
2. Mask source vsync via UART (`s`).
3. Confirm lock state transitions `LOCKED → HOLDOVER` within ~60 frames of ref loss.
4. Confirm MMCM correction value freezes at last-good value (read via UART).
5. Hold for 60 seconds in holdover. Measure drift via wrap velocity — should be near zero because the integrator is holding the correction that *was* matching the source.
6. Un-mask source vsync. Confirm transition `HOLDOVER → ACQUIRING → LOCKED` within settling time.

**Pass:**
- All state transitions observable on UART and GPIO lock LED.
- Free-run wrap velocity matches Test 1 baseline (proves zero-correction mode works).
- Holdover wrap velocity ≪ Free-run wrap velocity (proves integrator hold is doing useful work).
- Re-lock after holdover converges as quickly as initial acquire.

**Why it matters:** this is the user-facing behavior of the entire sync subsystem. If the UI lets the user pick `Reference: Genlock` and that path doesn't work, the product doesn't ship. Free-run and Input-lock are the same code paths the Genlock mode will use with a different mux input — proving them here proves the architecture.

**Debug info to log:** full state-transition timeline with timestamps. CSV. Useful as regression evidence when the reference mux gains additional inputs (Si5351, analog sync recovery).

## 6. What "done" looks like

The spike is done when:
- Tests 1–8 all pass.
- The CSVs from Tests 1, 3, 5, 6, 7, 8 are committed to the repo as evidence.
- A short summary doc captures: measured ppm offset, plant gain, loop BW, settling time, residual error, frame-slip rate under injected disturbance, state-transition timing.

At that point, the following architectural facts are proven on the bench:
- The MMCM-as-NCO actuator works on the Z-7020 (Tests 2, 3).
- A software-closed loop achieves sub-line phase control against a real reference (Tests 4, 5, 6).
- The dual-loop architecture (MMCM phase + VDMA cadence) cooperates correctly under over-range disturbance (Test 7).
- The reference selector and lock state machine work end-to-end, including Free-run and Holdover (Test 8).

What remains after the spike — per [`sync-architecture.md §7`](sync-architecture.md) — is **hardware integration**, not architecture changes:
- Wire the Si5351 / RP2040 output into the already-existing reference mux.
- Build the analog reference front-end (LTC / tri-level / black burst).
- Wire the Reference Select control to the UI.
- Schedule specific cadence ratios (60→50, 3:2, etc.) using the already-validated VDMA-slip mechanism.

None of those require revisiting the loop. The architecture is done at the end of the spike; the rest is fitting it into the chassis.

## 7. What the spike does **not** prove

Be honest about scope:

- It doesn't prove the loop can hold against an external reference with poor SNR (LTC recovered from a noisy analog input). That's a separate test once the front-end exists. The loop itself is reference-agnostic; what gets retested is the reference-recovery quality.
- It doesn't prove the 0.5 Hz production loop BW is correct — the spike will likely run at 5–10 Hz BW for fast convergence. Final BW tuning happens later, against real broadcast references.
- It doesn't validate specific cadence-conversion schedules (60→50 with its precise frame-slip cadence, 3:2 pulldown patterns, etc.). It proves the *mechanism* works; the specific schedules are configured per output-rate selection later.
- It doesn't test against extreme reference jitter, switching transients between reference sources, or simultaneous-multi-input edge cases. Production firmware will need defensive logic for those; the architecture supports it but the spike doesn't exercise it.

These are deliberate scope limits. The spike proves the foundation. The product is built on top of it, in subsequent passes — all of which are integration work, not architecture work.
