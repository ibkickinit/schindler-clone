# Projective front-end — Phase P1 results (sim-proven address generator)

**Scope:** P1 only — a simulation-proven projective (keystone + corner-pin / homography) address
generator that is a drop-in, port-compatible replacement for `pg_affine`. No BD, no bitstream, no
hardware. P2–P5 remain out of scope.

**Status: PASS.** `pg_projective` is bit-exact to the Python golden across affine-equivalence,
keystone H/V/HV, and a 4-corner pin, under both clean and random-backpressure drive.

## The math

Affine: `sx=a·ox+b·oy+c`, `sy=d·ox+e·oy+f`. Projective adds `w=g·ox+h·oy+i` (i=1), then
`sx=(a·ox+b·oy+c)/w`, `sy=(d·ox+e·oy+f)/w`. Numerators `nx`,`ny` and denominator `w` are all linear
in (ox,oy) → all three are incremental DDAs (no per-pixel multiply for them). The only new op is the
per-pixel reciprocal `iw=1/w`, then two multiplies `sx=nx·iw`, `sy=ny·iw`. Affine is the exact subset
`g=h=0,i=1` (w=1, iw=1).

## Reciprocal algorithm (pure Verilog, no LogiCORE)

LUT seed + Newton-Raphson, bit-exact between golden and HDL:

1. **Normalize** `w` (>0 in-frame) by leading-1 detect + barrel-shift into a mantissa `m∈[1,2)` with
   `RF` fractional bits (leading 1 at bit `RF`).
2. **Seed** `x0 = LUT[ top LUT_BITS of m's fraction ]` ≈ `1/m` (bin-center values, rounded).
3. **Newton-Raphson** `x ← x·(2 − m·x)`, `NR_ITERS` steps, **round-to-nearest** on every `>>RF` (so
   `1/(power-of-two)` lands exactly on the boundary — without this you get integer-coord off-by-ones
   at exact pixel boundaries, e.g. identity mapping 16.0 → 15.999…).
4. **De-normalize** `iw = x << (GFB − msb)` → `iw = (1/w_true)·2^RF`.
5. **Products** `sx_q = (nx_q·iw) >> RF` (Q.FB), likewise `sy_q`. Split to integer src_col/row + the
   top-12-bit Q0.12 fraction exactly as `pg_affine` exposes `o_h_frac/o_v_frac`.

A small-ε guard (`w ≤ ~1/64`) drives `o_in_window=0` (matte) — horizon / div-by-zero protection.

## Chosen widths / LUT / NR (the P1 precision budget)

| Param | Value | Why |
|-------|-------|-----|
| `FB` (numerator a..f frac bits) | **24** | Numerator coeff quant `2^-FB` is multiplied by `ox≈1280` then amplified by `1/w≈1.6` at the foreshortened edge. FB=12 gives ~0.5 px error there; FB=24 gets it under 2^-12. |
| `GFB` (perspective g,h frac bits) | **36** | g,h are tiny (~5e-4). Their quant error is amplified by `sx≈1872` at the edge. GFB=12 is catastrophic (~1900 px!); GFB=36 is needed. Word `GCW=40`. |
| `RF` (reciprocal datapath frac) | **28** | Reciprocal residual at RF=28 is ~1e-6 px — negligible vs the coeff-quant floor. |
| `LUT_BITS` | **9** | 512-entry seed ROM. Larger doesn't help (NR-limited, not seed-limited). |
| `NR_ITERS` | **2** | 1 iter is too coarse; 2 converges to machine precision for `m∈[1,2)`. |
| `AW` / `WW` | 44 / 48 | numerator / denominator accumulator widths (with headroom). |

**Achieved worst-case sx/sy error (LUT+NR fixed-point model vs float reference), 1280×720 out over
1920×1080 source, at the most-foreshortened edge:**

```
keystone-H 0.35   9.47e-05 px (~Q.13.4)  @ (1275,680)
keystone-V 0.35   8.23e-05 px (~Q.13.6)  @ (1275,714)
keystone-HV 0.30  1.21e-04 px (~Q.13.0)  @ (1275,697)
cornerpin-skew    7.23e-05 px (~Q.13.8)  @ (1020,714)
cornerpin-strong  1.05e-04 px (~Q.13.2)  @ (1275,714)
WORST OVERALL     1.21e-04 px (~Q.13.0)   >= the Q.12 (2.44e-04) target ✓
```

> **Key P1 finding:** projective mode needs *wider coefficient precision than affine* on BOTH coeff
> families, because both quantization errors are amplified by `1/w` at the foreshortened edge. The
> affine engine's Q.12 is fine for affine but ~0.5 px short for aggressive keystone. The HDL
> parameterizes `FB`, so the **production affine build keeps FB=12** (ports + GPIO unchanged); only
> the projective build pays Q.24 numerator + Q.36 perspective. The firmware homography solver (P4)
> emits coeffs in these formats.

## Handshake

Same advance-only-on-accept contract as `pg_affine`. The reciprocal is a fixed 8-stage pipeline; the
**entire datapath** (DDA front + reciprocal pipe + multiply) freezes as one unit whenever the output
is valid and the consumer is not ready (`pipe_en = !(o_valid && !o_ready)`). Nothing moves while
stalled → no coord is ever dropped or duplicated; throughput stays 1 px/clk. Proven in sim by the
random-`o_ready` backpressure passes (capture is keyed on accept, so raster alignment is automatic
regardless of latency/stalls).

## P5 timing-risk assessment

The current demand-fetch build is at **WNS +0.045 ns** on xc7z020-1 @ 74.25 MHz — razor-thin. The
projective additions land on (or adjacent to) the WNS-critical cache+coord cone:

- **Reciprocal pipeline (8 stages):** generously registered on purpose — every stage is a single
  multiply/shift/compare. The prefetch lead hides the latency (consumer + prefetch each get their own
  reciprocal; latency is free, throughput unchanged). Per-stage logic is light, so the reciprocal
  *itself* should not be the limiter, **but**:
  - The **two output multiplies** `nx·iw`, `ny·iw` are AW(44)×~31-bit. These MUST be forced to DSP48
    (`(* use_dsp = "yes" *)` or synth attribute) or LUT-based multipliers will blow the cone. The 7020
    has DSP headroom (+6 DSP per the scope). Recommend DSP48 for the 4 multiplies (2 per instance) and
    for the NR `m·x` multiplies (2 per instance) → ~6–8 DSP per engine; well within budget.
  - The **leading-1 detect** (`msb_of`, a 48-bit priority encoder) and the two **barrel shifts**
    (normalize, de-normalize) are each their own pipeline stage already — keep them isolated; do not
    let synthesis merge them with the seed-LUT read.
  - **`o_in_window`** is now derived from the post-divide `sx,sy` (was a pre-divide compare in affine).
    It's registered after the multiply, so it's off the critical handshake path — fine.
- **Coeff CDCs:** `m_g`,`m_h` are two NEW GPIO→pclk crossings. They MUST be false-pathed at P3, same
  trap as `lr1/dsel1/sr1` — every GPIO→pclk crossing. (P1 sim doesn't exercise CDC; flagged for P3/P5.)
- **Pipeline depth headroom:** if P5 closes short, the cheapest knobs are (a) add a register stage to
  split the multiply from the int/frac split, and (b) drop `NR_ITERS` to 1 is NOT viable (precision),
  but `RF` could trim 28→24 (saves a few bits on the NR multipliers) if the precision margin allows —
  the budget shows RF=24 still hits ~Q.13, so RF is a free timing knob.

**Bottom line for P5:** the design is pipelined deep enough that the *only* real timing exposure is the
multipliers; force them to DSP48 and false-path the two new coeff CDCs and it should close on the -1 at
74.25 MHz with margin comparable to the current build. Validate WNS empirically before committing.
